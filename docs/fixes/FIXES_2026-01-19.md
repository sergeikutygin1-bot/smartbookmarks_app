## Issue 1: Next.js Rewrite Rule Breaking API Routes

### Problem
`frontend/next.config.ts` contained a catch-all rewrite rule that intercepted **ALL** `/api/*` requests and proxied them directly to the backend, bypassing Next.js API routes entirely.

```typescript
// ❌ WRONG - This was breaking everything
async rewrites() {
  return [
    {
      source: '/api/:path*',
      destination: 'http://localhost:3002/api/:path*',
    },
  ];
}
```

### Symptoms
- 404 errors on `/api/graph/bookmarks/:id/related`
- 404 errors on `/api/bookmarks/:id/enrich`
- Cookie forwarding failures
- Authentication issues

### Root Cause
Next.js API routes are designed to:
1. Receive frontend requests
2. Forward them to backend with proper cookie handling
3. Return responses to frontend

The rewrite rule bypassed steps 1-3, sending requests directly to backend without authentication cookies.

### Fix
**File: `frontend/next.config.ts`**

```typescript
// ✅ CORRECT - No rewrites needed
const nextConfig: NextConfig = {
  output: 'standalone',
  experimental: {
    instrumentationHook: false,
  },
  // Note: We use Next.js API routes for proxying to backend
  // They handle authentication cookie forwarding properly
  // No rewrites needed - all /api/* routes are handled by Next.js API routes
};

export default nextConfig;
```

### Prevention
- **NEVER** add a catch-all rewrite for `/api/:path*`
- If you need to proxy new endpoints, create Next.js API route files in `frontend/app/api/`
- All backend communication MUST go through Next.js API routes for cookie forwarding

## Issue 2: Nested Dynamic Routes Not Working (Next.js 16 Issue)

### Problem
Route at `frontend/app/api/graph/bookmarks/[id]/related/route.ts` was returning 404 errors.

### Root Cause
1. Next.js 16 with App Router has issues with deeply nested dynamic routes like `/api/graph/bookmarks/[id]/related`
2. The rewrite rule was also interfering

### Fix
**Created catch-all route: `frontend/app/api/graph/bookmarks/[...slug]/route.ts`**

```typescript
import { NextRequest, NextResponse } from 'next/server';
import { getAuthHeaders } from '../../../auth-helper';

export const dynamic = 'force-dynamic';

const BACKEND_API = process.env.BACKEND_URL
  ? `${process.env.BACKEND_URL}/api/v1/graph/bookmarks`
  : 'http://localhost:3002/api/v1/graph/bookmarks';

export async function GET(
  request: NextRequest,
  context: { params: Promise<{ slug: string[] }> }
) {
  try {
    const { slug } = await context.params;

    // Expected: ['id', 'related']
    if (slug.length !== 2 || slug[1] !== 'related') {
      return NextResponse.json(
        { error: 'Invalid endpoint. Use /api/graph/bookmarks/:id/related' },
        { status: 404 }
      );
    }

    const id = slug[0];
    const url = `${BACKEND_API}/${id}/related`;
    console.log(`[GraphAPI] Fetching metadata from backend: ${url}`);

    const response = await fetch(url, {
      headers: await getAuthHeaders(request),
    });

    if (!response.ok) {
      console.error(`[GraphAPI] Backend returned status ${response.status} for bookmark ${id}`);
      if (response.status === 404) {
        return NextResponse.json(
          { error: 'Bookmark not found' },
          { status: 404 }
        );
      }
      throw new Error(`Backend returned ${response.status}`);
    }

    const data = await response.json();
    const conceptCount = data.data?.concepts?.length || 0;
    const entityCount = data.data?.entities?.length || 0;
    console.log(
      `[GraphAPI] Successfully fetched metadata for ${id}: ${conceptCount} concepts, ${entityCount} entities`
    );

    return NextResponse.json(data);
  } catch (error) {
    console.error('GET /api/graph/bookmarks/[...slug] error:', error);
    return NextResponse.json(
      { error: 'Failed to fetch bookmark metadata' },
      { status: 500 }
    );
  }
}
```

### Prevention
- For complex dynamic routes with multiple segments, use **catch-all routes** `[...slug]` instead of nested `[id]/path/route.ts`
- Always validate `slug` array contents before processing
- Test dynamic routes after any Docker rebuild

## Issue 3: Admin User Not Having Admin Role

### Problem
User `admin@smartbookmarks.app` was created with `role: 'user'` instead of `role: 'admin'`, causing 403 Forbidden errors on `/admin` endpoints.

### Root Cause
User registration endpoint (`/api/v1/auth/register`) defaults all users to `role: 'user'`. There's no automatic admin assignment.

### Fix
**Manual database update:**

```sql
UPDATE users
SET role = 'admin'
WHERE email = 'admin@smartbookmarks.app';
```

**Backend middleware check: `backend/src/middleware/adminAuth.ts`**

```typescript
export const adminMiddleware = async (req: Request, res: Response, next: NextFunction) => {
  // Check if user is authenticated
  if (!req.user) {
    return res.status(401).json({
      error: 'Unauthorized',
      message: 'Authentication required'
    });
  }

  try {
    // Get user from database to check role
    const user = await prisma.user.findUnique({
      where: { id: req.user.id },
      select: { role: true },
    });

    if (!user || user.role !== 'admin') {
      return res.status(403).json({
        error: 'Forbidden',
        message: 'Admin access required'
      });
    }

    next();
  } catch (error) {
    console.error('Admin middleware error:', error);
    return res.status(500).json({
      error: 'Internal server error',
      message: 'Failed to verify admin status'
    });
  }
};
```

### Prevention
**Create admin users properly:**

```bash
# 1. Register user normally
curl -X POST "http://localhost:3002/api/v1/auth/register" \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@smartbookmarks.app","password":"Admin123"}'

# 2. Manually grant admin role
docker exec <postgres-container> psql -U smartbookmarks -d smartbookmarks \
  -c "UPDATE users SET role = 'admin' WHERE email = 'admin@smartbookmarks.app';"

# 3. User must logout and login again to get fresh JWT with admin role
```

**Future Enhancement:** Create a CLI script or seed file for admin user creation.

## Issue 4: Docker Volume Mounts Don't Include next.config.ts

### Problem
Changes to `next.config.ts` were not reflected in the running container because the file is not volume-mounted.

**Current volume mounts in `docker-compose.yml`:**

```yaml
frontend:
  volumes:
    - ./frontend/app:/app/app
    - ./frontend/components:/app/components
    - ./frontend/lib:/app/lib
    - ./frontend/hooks:/app/hooks
    - ./frontend/store:/app/store
    - ./frontend/public:/app/public
```

**Note:** `next.config.ts` is NOT mounted!

### Fix
After modifying `next.config.ts`, you **MUST rebuild the Docker image**:

```bash
docker-compose build frontend
docker-compose up -d frontend
```

### Prevention
**Option 1: Add next.config.ts to volume mounts (Recommended)**

```yaml
frontend:
  volumes:
    - ./frontend/app:/app/app
    - ./frontend/components:/app/components
    - ./frontend/lib:/app/lib
    - ./frontend/hooks:/app/hooks
    - ./frontend/store:/app/store
    - ./frontend/public:/app/public
    - ./frontend/next.config.ts:/app/next.config.ts  # ADD THIS
```

**Option 2: Always rebuild after config changes**

If you modify `next.config.ts`, immediately run:
```bash
docker-compose build frontend && docker-compose up -d frontend
```

## Issue 5: Database Schema Mismatch After Git Reset

### Problem
After `git reset --hard`, Prisma schema changed but the database still had the old schema, causing errors like:

```
The column 'users.github_id' does not exist in the current database
```

### Root Cause
Git reset changed `backend/prisma/schema.prisma` but the PostgreSQL database wasn't updated.

### Fix
```bash
docker exec smartbookmarks_backend npx prisma db push --accept-data-loss
```

**⚠️ WARNING:** This wipes all existing data!

### Prevention
**After any git reset, checkout, or branch switch:**

```bash
# 1. Stop all containers
docker-compose down

# 2. Check if schema changed
git diff HEAD@{1} backend/prisma/schema.prisma

# 3. If schema changed, sync database
docker-compose up -d postgres
docker exec smartbookmarks_backend npx prisma db push --accept-data-loss

# 4. Start all services
docker-compose up -d

# 5. Recreate admin user if needed
```

**Better approach: Use migrations instead of db push**

```bash
# Create migration for schema changes
docker exec smartbookmarks_backend npx prisma migrate dev --name describe_your_changes

# Apply migrations
docker exec smartbookmarks_backend npx prisma migrate deploy
```

## Issue 6: Ghost Docker Container References

### Problem
Docker Compose kept referencing container `cb740e190426` that was manually removed, causing errors:

```
Error response from daemon: No such container: cb740e190426e8e40100fae90d410ee49a90832bba90a5aaf44bee157cff3e49
```

### Root Cause
Manually removing containers with `docker rm` or `docker container prune` breaks Docker Compose's internal state.

### Fix
```bash
# Clean approach
docker-compose down  # Stops and removes containers
docker-compose up -d # Recreates everything fresh
```

### Prevention
**NEVER manually remove containers created by docker-compose**

- Use `docker-compose down` to stop and remove
- Use `docker-compose restart <service>` to restart
- Use `docker-compose up -d --force-recreate <service>` to rebuild

**If you must manually manage:**
```bash
# Full reset
docker-compose down -v  # Removes volumes too
docker-compose up -d
```

## Key Files Reference

### Configuration Files
- `frontend/next.config.ts` - **No rewrites, standalone output**
- `docker-compose.yml` - Volume mounts (consider adding next.config.ts)
- `backend/prisma/schema.prisma` - Database schema

### Critical Routes
- `frontend/app/api/graph/bookmarks/[...slug]/route.ts` - Catch-all for graph endpoints
- `frontend/app/api/auth/login/route.ts` - Login with cookie setting
- `backend/src/routes/admin.ts` - Admin dashboard endpoints
- `backend/src/middleware/adminAuth.ts` - Admin role validation

### Authentication Flow
1. User submits credentials to `POST /api/auth/login` (Next.js API route)
2. Next.js route proxies to `POST http://localhost:3002/api/v1/auth/login` (backend)
3. Backend validates credentials, generates JWT tokens
4. Backend returns tokens in response with Set-Cookie headers
5. Next.js route extracts cookies from backend response
6. Next.js route sets httpOnly cookies on frontend domain
7. Frontend stores cookies, includes them in subsequent requests

### Admin Access Flow
1. User must have `role: 'admin'` in database
2. User must login to get fresh JWT with admin claim
3. Admin routes protected by `authMiddleware` + `adminMiddleware`
4. Middleware checks JWT validity and user role from database

## Common Mistakes to Avoid

### ❌ DON'T
1. Add rewrite rules for `/api/:path*` in next.config.ts
2. Manually remove Docker Compose containers
3. Use `prisma db push` in production (use migrations)
4. Modify next.config.ts without rebuilding Docker image
5. Create admin users without setting role in database
6. Git reset without syncing database schema

### ✅ DO
1. Create Next.js API route files for new backend endpoints
2. Use `docker-compose down/up` for container management
3. Use Prisma migrations for schema changes
4. Rebuild Docker image after config changes
5. Manually set admin role after user registration
6. Sync database schema after git operations
